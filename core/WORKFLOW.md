## Steer — classify before building
**Step 0 — ENTRY: a change is born UNGATED and earns its ladder.** RULE #1 (`core/FOUNDATIONS.md`) one level earlier — not *which findings block*, but *whether this change owes a review at all*. Four questions, before any gate is assumed: **1 · IRREVERSIBLE / LIVE** — money moved, corpus written, a send sent: can I **not** revert my way out? · **2 · SILENT FAILURE** — could this ship broken while looking fine? A failure that would not announce itself: controls, gates, checks, alarms, state/chain logic. · **3 · MULTIPLIED RADIUS** — does an error here leave this repo (template, kit, generated artifact)? · **4 · TEXT SOMEONE IMPLEMENTS** — will a person or agent execute these words? (ambiguity counts — the implementer picks). **FOUR NO's ⇒ BUILD: commit, run, revert IS the gate** — mechanical, instant, free, never tired, and it never manufactures a finding. **The doors decide ADMISSION; the decision tree sets DEPTH for admitted changes — it is not an entry test.** Accordingly: **any YES ⇒ ADMITTED — the tree's matching row is the depth.** *The warrant is measured, not argued: a gate on a change that did not need one is negative expected value — repairs generate repairs at near the rate the original code did, and roughly half of findings hit no harm target. The failure mode of most changes in a working repo is loud and cheap to undo; insurance above the price of the loss.* **The four doors are the ONLY doors — nobody re-derives their own entry test, and unsure whether a class applies ⇒ that IS a yes** (fail closed into the gate; cheap once). **The write-GO does not move, ever** — the execution axis is untouched by this rule, as by RULE #1. **The answer is RECORDED — one line in the commit body** (`entry: none` / `entry: class-N`): a judgment SURFACED, never a predicate. ⚠ **A COMMIT HOOK CHECKS ONLY ITS SHAPE; NO CONTROL CATCHES A FALSE ONE.** Its only judge is whoever next reviews the record — re-ask the four questions against what shipped and log ungated changes, plus any later implicated in a harm-target incident. **There is no audit and no cadence — this is the only catch:** an ungated change convenes no gate, so **a class-hit change that skipped its ladder is the gate-ran-lighter-than-mandate carve-out's case, raised when someone next reviews it, never a firing you can wait for.** **If ungated changes start biting, the four classes are drawn wrong and get REDRAWN**, never supplemented.

**Reversible** = a *tested, named restore-to-prior-state handle* confirmed by Owner before the write (snapshot · down-migration · delete-by-key only for pure INSERTs). Unverified backup/export or UPDATE-delete is not restoration. No handle ⇒ **irreversible** (an action flag, below).

**Decision tree for new work — first match:**
1. Live-prod write or deployment, **live-behavior-path** code, or **chain/stateful control logic** → **T2 Major**.
2. **Local, no live-prod write** (test, tool, local DB, *bounded* read-only prod query) → **T1 Minor** if Step 0 admits it.
3. **Local, non-code** (docs, comments, log string, memory pointer) → **T0 Trivial** if no stronger controlling-doc rule applies.

For an **unbounded production read**, bound rows, time, memory and concurrency, or use an offline artifact. Otherwise hold execution and route risk/budget through Principal to Owner. Relabeling grants no execution authority. Genuine T0 keeps its self-check; controlling instructions keep their stronger gate.
**Action flags**, from concrete effects, never labels: **irreversible** · **money/ledger** · **auth/credential**. A flagged change is at least T2; each flag ADDS a **REQUIRED cross-family lens** (same-family-only never discharges it), the **frontier · xhigh** gate (`core/GATES.md` matrix) and a **named Owner GO per write**.

Builder proposes tier; **recorded Principal delegation covers ordinary in-scope tier/wording through PM. Owner retains critical intent, material scope/budget/access, risk acceptance, irreversible deletion, credential/access change, money/new spend, and exact push/deploy/publication/live/external-write GO.** Split separable tiers; otherwise use the highest. Tier sets review depth; action sets execution authority. ⚠ **RULE #1 cuts REPAIRS, never review DEPTH — cutting seats is the misreading. New work is never T3: it is T2 plus its action flags. Historical T3 retains its original depth.**

| Tier | Code gate | Execution gate *(only if prod write)* |
|---|---|---|
| **T0** | pre-flight → self-check → proceed | — |
| **T1** | pre-flight → one blind cold reviewer (**cross-family by default**) → proceed | — |
| **T2** | pre-flight → **contract lens, PRE-CODE** → cold panel (≥2 angles + free) → cross-family lens [if avail; REQUIRED if flagged] → external → Owner push-GO | reversible: Owner GO may cover a bounded batch; irreversible: **named Owner GO per write** + `core/OPERATE.md` safeguards |

**Historical T3** keeps ≥3 angles + free, required lens + external, and Owner obligations through closure and descendants. New v4 roots/children are T2 only; declarations cannot prove T3 lineage.

**Rung ORDER binds — two rules, wherever a tier has that rung** (seats and invocation in
`core/GATES.md` § Routing; the commands in § Pre-flight are advisory, this ordering is not).
**No mechanism enforces either, and they are NOT equally checkable — say which is which rather than
implying both are covered:** rule 2's compliance is a manifest field (`pass-type`), so it is recorded
per seat and the Owner spot-checks it; rule 1's is not — nothing in the verdict record captures *when*
the lens fired relative to the code existing, so it is **self-report only**, exactly like the tier
declaration below.
1. **The BUDGET-FREE rungs run FIRST** — the deterministic pre-flight, and at T2/T3 **one**
   cross-family lens firing on the **contract, before any code exists**. A wrong contract faithfully
   implemented still ships the defect: the cheapest failure to kill early and the dearest to kill
   late, and no amount of code review finds a defect the contract authorised. It is **one** firing,
   not a second lens seat — the code-stage lens still fires per the tier row.
2. **The DISCOVERY rung runs `free`** — no prior findings, no verdicts, no rationale
   (`core/REVIEW.md` § Decorrelation's canonical pass-type). That is T1's single seat and T2/T3's
   blind panel. Its value is seats taking *divergent* paths outside the packet; one shared fact-pack
   picks one path and every seat inherits it. **"The budget-free rungs cleared it, so the panel can be
   lighter" is FORBIDDEN:** a budget-free rung may stop the work, but it never reduces the panel's
   depth, scope, or seat count.

*Tier table = local build/run depth; every remote push or publication needs a fresh Owner GO for the exact head and target (see "Pushing is a separate axis").*
**The tier is declared and approved under above authority** — a declaration is a self-report, and no mechanism can tell a correctly-tiered change from a mis-tiered one. **Escalate mid-task freely; lowering mid-task requires the Owner's confirmed reversibility handle (above) and is recorded in the PM disposition.** *(This binds the PM and Owner — **no mechanism enforces it**; a hook cannot tell a dodge from an Owner-authorised correction. `guard-gate-ladder.mjs` only surfaces a ladder — the declared tier's for `in-thread`, and the **strictest** for every other state, including a tiered `exempt`, whose tier it deliberately does **not** honour (honouring it would route to a LOWER tier, i.e. fail-OPEN in a sensor) — failing closed to T3, and never denying. Since kit v2.1 it registers in **both** lanes; the Codex-lane registration is inert until a human grants hook trust, and an untrusted hook is skipped silently.)*

**Autonomy local, boundaries central:** T0/T1 the Builder builds and runs locally free; T2 adds an external adversary.

**Pushing is a separate axis from the tier** (the push *is* the deploy where the target auto-deploys): **every remote push or publication needs a fresh Owner GO for the exact head and target, regardless of tier or file type**. A tier governs build/local-run depth; reaching the auto-deploy target is always re-gated.

**Core-document amendments are never T0** (high leverage: a doctrine flaw propagates). Gate depends on whether anything FOLLOWS the text. **Text something follows — gate machinery, seat definitions, designs and plans code will implement, binding templates → FULL T2: panel + wording approval under above authority** (gate machinery also keeps the adversarial walk-through). **Text nothing follows — records, history, README-class description → ONE blind cold reviewer.** Cross-family except REVIEW fallback; **wording approval under above authority**; **no external gate** (no code to verify; an idea's substance is the Owner's call). That approval closes the core-document gate only; it is never a review or remote-publication GO. Every remote push or publication still needs a fresh Owner GO for the exact head and target. **For PROSE this caps the gate SHAPE at every tier, and the EXTERNAL GATE ONLY:** escalation raises depth, never re-adds the external gate, and the **cross-family lens stays REQUIRED under an action flag or at historical T3**. *Exception:* an amendment carrying **executable content** (schemas, an API contract code depends on) follows the **code tiers** for that portion — **the prose cap does NOT reach it; that portion still owes its tier's external gate** (`core/ARTIFACT_CLASS.md` § Artifact-class review physics, rule 6). **Amendments to the gate machinery itself** — *any clause that sets a tier, a gate trigger, a NO-GO condition, a reviewer payload, an invariant, or a mitigation/manifest schema (if in doubt, it is)* — require an **adversarial walk-through** — ≥1 reviewer constructs a concrete scenario where an agent technically *complies* yet the targeted failure still occurs — before sign-off; design-mode prose-reading alone is insufficient. Core docs are listed in `core/BINDINGS.md`.

### Architectural consult routing

With recorded Owner delegation, persistent Architect is Project Principal: it drives completion and decides
ordinary in-envelope questions; directives bind PM, advice/reviews do not. PM is sole execution chain. A blocked
method goes with exact evidence to Principal; valid ordinary retry proceeds, otherwise hold it and route an unresolved
reserved exception once through Principal to Owner. Detail: installed `/architect-build` routing.

**Before building:** state user-visible done and proof; for T2/T3 write intent + falsifiable acceptance criteria before coding; for chain/stateful logic name and test crash, retry, corrupt-state, starvation, and empty-tick cases before the gate.

## Gate — the review ladder
*The ladder itself is below. **How a review is constructed and judged** — the cold-review payload contract, decorrelation, the cross-family lens, and the external gate — is `core/REVIEW.md`. **Tool invocation** (Codex / Gemini runners, model-effort matrix, receipts, traps) is `core/GATES.md`.*

Unavailable: no verdict; use REVIEW fallback.

**Before the contract is written, run the pre-flight** (`core/GATES.md` § Pre-flight).

**RE-VERIFY A VERSION-SPECIFIC FLAG BEFORE RELYING ON IT, NOT ONLY BEFORE DROPPING IT.** Where a rung rests on version-pinned tool behaviour, the verification expires when the tool moves and the rung expires with it. A one-directional clause (*"re-verify before dropping"*) **never fires, because nobody drops a flag they were told to keep.** *Instance: a 2026-07-17 check was **CORRECT WHEN MADE**. Compression kept its outcome and dropped the version that was its warrant, beside a copy-paste line; two CLI generations on, the behaviour had reversed and the instruction produced the failure it prevented, at exit 0 — and the exposed operator was the careful one following the documented hand-run.* ⇒ **A version-pinned claim carries the version it was proven on; a re-add costs a fresh proof, not a memory.** Symptoms: `core/GATES.md` § Gotchas / traps.

**Enumerate the mandated rungs BY CITATION before the gate runs.** List every rung *this* repo's doctrine mandates for the declared tier **and** the artifact's class — naming file and section, and quoting enough of each clause to survive renumbering, because a line number alone is a moving reference. **This creates no stop condition and blocks nothing:** the mandated rungs bind whether or not you enumerate them, so enumerating changes what you KNOW, never what the gate requires. Read them; do not recall them, and do not inherit a brief whose gate spec is lighter than the mandate. **Prior rounds are never a reason to run a lighter one** — a spec below the mandate is an under-scope however many verdicts preceded it (rung-order rule 2 above). **Nothing enumerates this list for you:** `guard-gate-ladder.mjs` surfaces the *declared* tier's ladder and never denies (§ Steer), and `sensor-sweep-owed` reminds you of exactly ONE rung — the dependency sweep below — keyed on the file's class, never on the clause that mandates it. Nothing reads the rest, so an unenumerated rung is indistinguishable from a discharged one right up until a seat runs it. The rung most often missed is the one a *general* tier row does not mention because a **narrower clause elsewhere adds it**, so enumerate against the artifact's class and file set, not the tier row alone.
**Amending a `CLASS: BINDING` document owes a dependency sweep before the edit is folded** — `/sweep`, whose report states its own coverage. **It is a ceremony, not a proof: the sweep's file list is chosen by whoever runs it, so a report closes nothing on its own.** ⚠ **AUDIT THE VERIFIER ITSELF: A BLIND VERIFICATION TOOL RETURNS SUCCESS.** A checker that cannot reach its target reports **nothing found**, not *"I could not look"* — and nothing-found is shaped like all-clear. Ask what a control would emit if it could not inspect; if that is a clean report, its green means only that it ran. *Instance, found inside its own fix: **the sweep runner itself was launching its seat with file access disabled**, so it would have attested every file scanned and exited 0.* **Prove the tool can see before you believe what it did not find.** **Sweep by CLAIM — never by authorship or filename.** The question is which *other* lines assert something this edit makes FALSE — same file, same section, and any sibling doc the same changeset edits — not which lines you happen to have written. **A surface the changeset does NOT edit is outside this sweep** and stays hand-synchronised; saying so is the point, because a sweep believed to be wider than it is closes a gap it never covered. And one claim has several spellings: a figure, its unit-converted twin and the prose that paraphrases it are one claim in three renderings, so **a grep proves a SPELLING, never a claim** (`core/INVARIANTS.md` rule 8 is the code-side twin), and an "absent" result earns one look at the raw material before you believe it. **No mechanism performs any of this.**

**Gate states.** FAIL → stop the gate → PM verifies and dispositions each finding (rubric below); `DEFER`/`DECLINE` → record and do not edit. Cold vs external disagreement is evidence for PM adjudication, not automatic severity-maxing. Mis-tier discovered → escalate; missed depth runs at the next round, or at the bookend via a typed successor — never an in-place restart.

**A verdict is INPUT, not an instruction; a ladder ends on a JUDGMENT, never on reviewer silence** — an adversarial reviewer never runs out of findings, so *"no findings left"* is unreachable and must never be an exit condition. **Emit the disposition after EVERY verdict, before any edit; no emission ⇒ no fix** (an undispositioned fix is out-of-process — revert it):
> `GATE ROUND <n> · changeset <name> · verdict <GO|NO-GO> · HARM-PASSING <h> · NOTES <k> · ACTION-SCREEN <—|named per RULE #1>` — per finding, **IN ORDER, first exit wins**: **HARM?** *(does this hurt **(1) the Owner/user, (2) the usability of the product, or (3) the FUNCTIONALITY of the code** — and by what **mechanism**? **Blank ⇒ NOTE** *(Precedence below and the carve-outs — irreversible · prod write · gate-ran-lighter-than-mandate — screen FIRST; none exit here)*: recorded here.)* · **REAL?** *(does it occur in the **declared** threat model? No ⇒ `DEFER` + the failed trigger.)* · **SCOPE?** *(the FEATURE asked for, or machinery **you wrote about yourself**? A self-authored invariant ⇒ **fix the SENTENCE, never the code** — a line, not a round.)* · **WORTH IT?** *(does the harm named above outweigh **the cost of chasing it** — time, tokens, and the repairs the repair itself generates?)* → **REMEDIATE | DEFER | DECLINE | ESCALATE** + reason. The pricing flip: dropping a harmless finding is FREE; chasing one owes the work. The ratio is not optional — a round without it is unscreened. **Every `REMEDIATE` — CODE, PROSE, DOCTRINE, EVERY class — carries `HARM:` *and* `TRIGGER:`:** for code a reachable path (inputs/state → the bad outcome, runnable or derivable from the diff); for prose **who reads it and what wrong action follows**. A REMEDIATE lacking either is out-of-process (revert the fix). **A REMEDIATE discharges only when the finding's OWN trigger is re-run and no longer fires** — a new test passing is not discharge. **Symmetric brake — a `NOTE`, `DEFER` or `DECLINE` of a reviewer-rated BLOCKER/HIGH owes the failed case: for a NOTE the FAILED HARM (which targets you tested, why each misses); otherwise the FAILED trigger: the strongest trigger you could build + the specific reason it is out-of-model / unreachable / an accepted residual — never bare absence, and never "the Owner didn't recognise it" (verify reachability against the code). Precedence still forbids deferring a *confirmed* material failure** *(it already HAS both, so it REMEDIATEs)*. Close: `LADDER: continue | STOP-AND-ESCALATE`.

**Disposition brake.** `DECLINE`/`DEFER` are first-class. A round with findings but NO notes, or whose findings are *every* `REMEDIATE`, pauses for an **in-thread self-audit** of the threat model, each `HARM:` and each `TRIGGER:`. Escalate only if one fails or scope drifts; real multi-bug rounds do not interrupt the Owner. **Rounds continue only while each new one is warranted by NEW HARM-passing findings** — no new harm, no new round; the R4 bookend excepted: it ALWAYS runs.

**Round/root-cause controller — finite aggregate cadence.** `panel_open` binds the frozen commit/tree, tier and complete seats; `panel_close` collects them; the orchestrating PM partitions every finding and declares repeated mechanism. R1 permits one bounded batch unless repeated. Harm-bearing R2 and repeated R1 require one shared-cause `root_replacement`, `simplification`, or `split`, plus a root exit with closure evidence. At that R2 checkpoint, consult the frontier now when the correction changes design, makes a product tradeoff, or needs more than one additional repair round. R3 tests the consolidated correction. Dispatch into R4 requires a fresh frontier process review bound to the latest close and frozen candidate: `finish_bounded_root` permits the one bounded finish; `successor` stops current repair and records future work after terminal close; `owner_decision` grants no current-chip dispatch. When process review is required, a terminal child uses a fresh child-purpose review bound to that terminal anchor and exact proposal. R4 is the final bookend and has no outgoing dispatch. **Once before closing, it re-screens every accepted blocker against the candidate *as-shipped*** (`core/FOUNDATIONS.md` RULE #1): a trigger that no longer fires is a named residual; one that fires survives. Zero survivors closes `GO`; any closes `STOP` with a narrow-successor-or-abandon recommendation. Critical/fail-open harm may STOP at any round; zero accepted harm may GO. Non-blocking adjacents route as FOLLOW-UP. No R5, cycle, reset, or audit window. The controller governs T2/T3. Gate ordinals accumulate through descendants; every next ordinal divisible by four needs a fresh frontier review before work authority, never an extra round. One same-round refreeze before R4 grants no batch or count. STOP or a collected-panel close reserves reviewed paths; only an Owner child or T2 Principal-evidenced split/new child confined to opened paths can rework them; the parent stays terminal. **Zoom-in and zoom-out gate every scope, disposition and root call; disagreement means delete, simplify, split, or escalate. KISS: remediation cannot become the product or dominant defect source.**

**Rounds count per changeset — task, not file version:** refreezes, finding splits, or reviewer swaps never reset it. Authors declare the four-bucket finding partition, each follow-up's routing, and the batch kind; automation checks shape and surfaces candidates, never semantic sameness. **Stop earlier on SCOPE signals:** last-round code causes the finding · fix needs a contract change · wrong threat layer. Declare threat model + residuals before Round 1 (`core/REVIEW.md`); otherwise declare them with the Owner. Out-of-model/residual findings are `DEFER`. **A false premise stops work.**

The Git-common controller is first-wins; absent/v2/v3 history replays unchanged; a v3 or T3 program (or, with none, pending lineage) keeps minting v3; otherwise v4 mints explicitly. After R4 STOP, one Owner completion child needs fresh `owner_decision`; bounded T2 Principal completion needs `successor` and opened-only paths. Either gets one verified batch and final full panel at the inherited ordinal. Parent stays terminal: no sibling, descendant, second batch, extra panel, reset, or repeat. The guard rechecks session, brief bytes, and target; shell writes stay outside it.

**PM finding disposition — reviewers surface; the orchestrating PM decides.** A verdict is not a work order. **HARM-fail is a NOTE.** `REMEDIATE` needs a reachable supported-use trigger causing a false result, data loss, unauthorized access, service failure, or material resource exhaustion. Quality preferences, out-of-model attacks, unsupported environments, and defenses for remediation-only machinery are `DECLINE` or `DEFER`; green acceptance evidence moves useful non-blockers to parent-linked successors. Otherwise: **REMEDIATE** (harm-passing and material); **DEFER** (real, non-material; named successor/backlog); **DECLINE** (false or unsupported); **ESCALATE** (Owner intent/risk). Severity is evidence; the PM verifies and weighs likelihood × impact × repair cost. **Precedence:** a confirmed invariant or material correctness, security, safety, provenance, reversibility/blast-radius, deploy-order, contract/additive, IO, or mitigation-integrity failure requires `REMEDIATE`, or `HOLD` + `ESCALATE`. Map: REMEDIATE⇒`accepted` · DEFER⇒`followup` · DECLINE⇒`declined` · HARM-fail⇒`note`; ESCALATE/`HOLD` needs STOP or Owner close. Risk acceptance remains `HOLD—OWNER-ACCEPTED CONTAINMENT` (default-off · quarantine · non-prod), never a pass.

**Final-gate rule — every material repair is reviewed in its next aggregate round.** PM fixes only accepted **REMEDIATE** findings and reruns their original triggers in the round's single batch. The next frozen candidate receives the full precommitted panel; no seat-by-seat repair or clean-pass chase occurs. **If the changeset's frontier firing is unspent, the remediation delta receives it as a fold-check** (`core/GATES.md` § Model · effort matrix), and the approved delta one cross-family bookend when available — *code* in diff-mode; *design/core-doc* in design-mode on the full updated artifact — or one same-family cold re-review when the lens is unavailable. The final PM partition may close `GO` with declined/deferred/NOTE evidence when no accepted blocker remains; any accepted blocker closes `STOP`.

**Shipping — remote publication.** Any remote push or publication to the live / auto-deploy target needs the applicable code gate plus a **fresh named Owner GO** for the exact head and target — never a routine push. A tier sets the local gate, not remote authority. If the pushed code carries a prod-write path, the push-GO authorizes the *deploy* only; each prod write it then performs takes its own named **write-GO** (the two are never merged).
