## Steer — classify before building
**Reversible** = a *tested, named restore-to-prior-state handle* exists before the write AND the Owner confirms it at classify-time (snapshot id · verified down-migration · delete-by-key *for pure INSERTs* — on an UPDATE it deletes rather than restores prior state, so a mutating write needs a snapshot/down-migration or is T3). A raw, unverified backup/export does **not** count. No confirmed handle ⇒ **irreversible**; Builder proposes **T3** until the Owner confirms a handle to downgrade.

**Decision tree — first match, evaluate 1→4:**
1. Executes (or deploys code that will execute) an **irreversible** write to live prod → **T3 Critical**
2. A **reversible** write to live prod, OR changes **live-behavior-path** code, OR changes **chain/stateful control logic** → **T2 Major**
3. **Local — touches no live prod** (a test, a local tool/script, a local-DB mutation, a *bounded* read-only prod query) → **T1 Minor** *(an **unbounded** prod read is **T3** — OOM risk; download an artifact instead)*
4. **Local, non-code** — docs, comments, a log string, a memory pointer → **T0 Trivial**

Builder proposes the tier; **Owner ratifies before any T2/T3 gate.** A change bundling separable tiers → split into separately-gated commits; only when inseparable does the whole take the highest tier. The tier sets a **code gate** (review depth) + an **execution gate** (run authorization, only if it runs a prod write).

| Tier | Code gate | Execution gate *(only if prod write)* |
|---|---|---|
| **T0** | pre-flight → self-check → proceed | — |
| **T1** | pre-flight → one blind cold reviewer (**cross-family by default**) → proceed | — |
| **T2** | pre-flight → **contract lens, PRE-CODE** → cold panel → cross-family lens [if avail] → external → Owner push-GO | named-GO (may cover a bounded batch) + execution protocol |
| **T3** | pre-flight → **contract lens, PRE-CODE** → cold panel → **both** cross-family families (lens **required** + external) → Owner push-GO | **named-GO per write** + execution protocol |

**Rung ORDER binds — two rules, wherever a tier has that rung** (seats and invocation in
`core/GATES.md` § Routing; the commands in § Pre-flight are advisory, this ordering is not).
**No mechanism enforces either, and they are NOT equally checkable — say which is which rather than
implying both are covered:** rule 2's compliance is a manifest field (`pass-type`), so it is recorded
per seat and the Owner spot-checks it; rule 1's is not — nothing in the verdict record captures *when*
the lens fired relative to the code existing, so it is **self-report only**, exactly like the tier
declaration below.
1. **The BUDGET-FREE rungs run FIRST** — the deterministic pre-flight, and at T2/T3 **one**
   cross-family lens firing on the **contract, before any code exists**. A wrong contract faithfully
   implemented still ships the defect: the cheapest failure to kill early and the dearest to kill
   late, and no amount of code review finds a defect the contract authorised. It is **one** firing,
   not a second lens seat — the code-stage lens still fires per the tier row.
2. **The DISCOVERY rung runs `free`** — no prior findings, no verdicts, no rationale
   (`core/REVIEW.md` § Decorrelation's canonical pass-type). That is T1's single seat and T2/T3's
   blind panel. Its value is seats taking *divergent* paths outside the packet; one shared fact-pack
   picks one path and every seat inherits it. **"The budget-free rungs cleared it, so the panel can be
   lighter" is FORBIDDEN:** a budget-free rung may stop the work, but it never reduces the panel's
   depth, scope, or seat count.

*Tier table = local build/run depth; any code **push** also needs an Owner push-GO (see "Pushing is a separate axis").*
**The tier that selects the row is the DECLARED one, Owner-ratified per above** — a declaration is a self-report, and no mechanism can tell a correctly-tiered change from a mis-tiered one. **Escalate mid-task freely; lowering mid-task requires the Owner's confirmed reversibility handle (above) and is recorded in the PM disposition.** *(This binds the PM and Owner — **no mechanism enforces it**; a hook cannot tell a dodge from an Owner-authorised correction. `guard-gate-ladder.mjs` only surfaces a ladder — the declared tier's for `in-thread`, and the **strictest** for every other state, including a tiered `exempt`, whose tier it deliberately does **not** honour (honouring it would route to a LOWER tier, i.e. fail-OPEN in a sensor) — failing closed to T3, and never denying. Since kit v2.1 it registers in **both** lanes, but read `core/BINDINGS.md` § Enforcement asymmetry as part of that: the Codex-lane registration is inert until a human grants hook trust, and an untrusted hook is skipped silently.)*

**Autonomy local, boundaries central:** T0/T1 the Builder builds and runs locally free; T2 adds an external adversary; T3 stops at the Owner.

**Pushing is a separate axis from the tier** (the push *is* the deploy where the target auto-deploys): **docs-only (T0) pushes without a GO (unless the branch carries unpushed code — a push ships the whole branch); any push containing code needs an Owner push-GO regardless of tier** — T1 code: cold + push-GO; T2/T3: cold + external + push-GO. A tier governs build/local-run depth; reaching the auto-deploy target is always re-gated.

**Core-document amendments are never T0** (no prod blast-radius, but high leverage — a doctrine/architecture flaw propagates to every change under it). Gate = **blind cold pass** (panel ≥2 for a substantial change; a single reviewer for a minor clause) → **Owner sign-off on the wording**; **no external gate** (no code to verify; an idea's substance is the Owner's call). The Owner wording sign-off also stands as its push-GO. **For PROSE this caps the gate SHAPE at every tier, and the EXTERNAL GATE ONLY:** escalation raises depth, never re-adds the external gate, and the **cross-family lens stays REQUIRED at T3** — the T3 row bundles both seats in one cell, so reading the cap across it would drop one that is not capped. *Exception:* an amendment carrying **executable content** (schemas, an API contract code depends on) follows the **code tiers** for that portion — **the prose cap does NOT reach it; that portion still owes its tier's external gate** (`core/ARTIFACT_CLASS.md` § Artifact-class review physics, rule 6). **Amendments to the gate machinery itself** — *any clause that sets a tier, a gate trigger, a NO-GO condition, a reviewer payload, an invariant, or a mitigation/manifest schema (if in doubt, it is)* — require an **adversarial walk-through** — ≥1 reviewer constructs a concrete scenario where an agent technically *complies* yet the targeted failure still occurs — before sign-off; design-mode prose-reading alone is insufficient. Core docs are listed in `core/BINDINGS.md`.

**Before building:** recommend the intelligence tier; for T2/T3 write **intent + falsifiable acceptance criteria** as a design doc *before* coding; for chain/stateful logic name the **adversarial cases up front** (crash-mid-sequence · retry · corrupt-state→fail-closed · starvation · empty-tick) and write them as tests before the gate.

## Gate — the review ladder
*The ladder itself is below. **How a review is constructed and judged** — the cold-review payload contract, decorrelation, the cross-family lens, and the external gate — is `core/REVIEW.md`. **Tool invocation** (Codex / Gemini runners, model-effort matrix, receipts, traps) is `core/GATES.md`.*

**Before the contract is written, run the pre-flight** (`core/GATES.md` § Pre-flight).

**Enumerate the mandated rungs BY CITATION before the gate runs.** List every rung *this* repo's doctrine mandates for the declared tier **and** the artifact's class — naming file and section, and quoting enough of each clause to survive renumbering, because a line number alone is a moving reference. **This creates no stop condition and blocks nothing:** the mandated rungs bind whether or not you enumerate them, so enumerating changes what you KNOW, never what the gate requires. Read them; do not recall them, and do not inherit a brief whose gate spec is lighter than the mandate. **Prior rounds are never a reason to run a lighter one** — a spec below the mandate is an under-scope however many verdicts preceded it (rung-order rule 2 above). **Nothing enumerates this list for you:** `guard-gate-ladder.mjs` surfaces the *declared* tier's ladder and never denies (§ Steer), and `sensor-sweep-owed` reminds you of exactly ONE rung — the dependency sweep below — keyed on the file's class, never on the clause that mandates it. Nothing reads the rest, so an unenumerated rung is indistinguishable from a discharged one right up until a seat runs it. The rung most often missed is the one a *general* tier row does not mention because a **narrower clause elsewhere adds it**, so enumerate against the artifact's class and file set, not the tier row alone.
**Amending a `CLASS: BINDING` document owes a dependency sweep before the edit is folded** — `/sweep`, whose report states its own coverage. **It is a ceremony, not a proof: the sweep's file list is chosen by whoever runs it, so a report closes nothing on its own.** **Sweep by CLAIM — never by authorship or filename.** The question is which *other* lines assert something this edit makes FALSE — same file, same section, and any sibling doc the same changeset edits — not which lines you happen to have written. **A surface the changeset does NOT edit is outside this sweep** and stays hand-synchronised; saying so is the point, because a sweep believed to be wider than it is closes a gap it never covered. And one claim has several spellings: a figure, its unit-converted twin and the prose that paraphrases it are one claim in three renderings, so **a grep proves a SPELLING, never a claim** (`core/INVARIANTS.md` rule 8 is the code-side twin), and an "absent" result earns one look at the raw material before you believe it. **No mechanism performs any of this.**

**Gate states.** FAIL → stop the gate → PM verifies and dispositions each finding. `REMEDIATE` → fix → scoped bookend; `DEFER` / `DECLINE` → record and do not edit; `ESCALATE` → Owner. Cold vs external disagreement is evidence for PM adjudication, not automatic severity-maxing. Mis-tier discovered → escalate and restart the required gates.

**A verdict is INPUT, not an instruction; a ladder ends on a JUDGMENT, never on reviewer silence** — an adversarial reviewer never runs out of findings, so *"no findings left"* is unreachable and must never be an exit condition. **Emit the disposition after EVERY verdict, before any edit; no emission ⇒ no fix** (an undispositioned fix is out-of-process — revert it):
> `GATE ROUND <n>/3 · changeset <name> · verdict <GO|NO-GO>` — per finding: **REAL?** *(does it occur, in the **stated** threat model? reachable?)* · **SCOPE?** *(the FEATURE asked for, or machinery **you** introduced?)* · **BOUNDED?** *(small and final, or does it mint new surface — and what working thing could this fix break?)* · **WORTH IT?** *(what breaks if you DECLINE?)* → **REMEDIATE | DEFER | DECLINE | ESCALATE** + reason. **A `REMEDIATE` on CODE must carry a `TRIGGER:` line — a concrete reachable path in the *declared* threat model (inputs/state → the bad outcome, runnable or directly derivable from the diff); no trigger ⇒ `DEFER`/`DECLINE`, and a REMEDIATE lacking one is out-of-process (revert the fix).** **Symmetric brake — a `DEFER`/`DECLINE` of a reviewer-rated BLOCKER/HIGH owes the FAILED trigger: the strongest trigger you could build + the specific reason it is out-of-model / unreachable / an accepted residual — never bare absence, and never "the Owner didn't recognise it" (verify reachability against the code). Precedence still forbids deferring a *confirmed* material failure.** *(= instruction-physics "reproduce before folding" promoted to code — `core/ARTIFACT_CLASS.md`; composes with Precedence below — a mechanically-confirmed failure already HAS its trigger, so it still REMEDIATEs.)* Close: `LADDER: continue | STOP-AND-ESCALATE`. After round 3 add `PAST-SOFT-STOP: CONTINUE | STOP-AND-ESCALATE` + a specific `JUSTIFICATION` if continuing.

**`DECLINE`/`DEFER` are first-class, and ALL-REMEDIATE forces a self-audit:** a round whose findings are *every* `REMEDIATE` (>1 finding) pauses the ladder for a mandatory **in-thread self-audit** — re-read the threat-model contract and re-verify each `TRIGGER` actually holds; continue on a clean audit, and **escalate the scope to the Owner ONLY if a trigger does not hold or scope is drifting.** A clean multi-bug round is normal (a first cold panel routinely finds several real bugs) and does NOT interrupt the Owner — this is the backstop for a fabricated `TRIGGER`, not a tax on real bugs. **Soft stop after 3 NO-GO rounds per CHANGESET.** Round 4+ may continue without Owner presence only after the PM emits the repeated warning plus a specific justification naming what changed, why another cycle is warranted, and why it is bounded rather than scope churn. **Rounds count per changeset — the task, not the file version:** re-freezing after a fix, splitting findings, or swapping reviewer/family does **not** reset the count. **Stop earlier on any SCOPE signal:** findings arriving *in code you added last round* · the fix needs a contract edit · unreachable in the threat model, unfixable at this layer, or a nit. **Declare the threat model + accepted residuals BEFORE round 1 and hand them to the reviewer** (`core/REVIEW.md` contract); **undeclared ⇒ the gate's first act is declaring it with the Owner** (Owner-ratified like the tier — an inflated/adversarial model needs explicit Owner scope, so a fabricated `TRIGGER` naming an out-of-model actor has nothing to stand on). A finding outside that model or inside the residual set is `DEFER` by construction, not re-adjudicated (gates are seatbelts for cooperative agents, not intrusion detection — `core/FOUNDATIONS.md` § Principles, Threat-model calibration). **A false premise stops the work:** report it; never silently reinterpret and build. *(`<n>` is a CONVERSATION fact — verdicts dispositioned. **No hook counts it**; a round-counting hook was retired 2026-07-18. Origin: `docs/journal/workflow_v2_phase3_design.md`.)*

**PM finding disposition — reviewers surface; the frontier PM decides.** A review verdict stops the current gate, but it is not an automatic work order. Before editing, the PM records each finding as: **REMEDIATE** (confirmed or reproducible and material to the contract, acceptance criteria, or a required gate dimension); **DEFER** (real but non-material to this release; named backlog/ticket); **DECLINE** (false positive, unsupported speculation, cosmetic nit, or disproportionate non-material edge case); or **ESCALATE** (requires Owner intent/risk judgment). Severity is evidence, not authority: the PM verifies the claim, weighs likelihood × impact × remediation cost, and owns the release-level verdict. **Precedence:** a mechanically confirmed invariant failure or material correctness, security, safety, provenance, reversibility/blast-radius, deploy-order, contract/additive, IO, or mitigation-integrity failure cannot be `DEFER`red or `DECLINE`d; it requires `REMEDIATE`, or `HOLD` + `ESCALATE`. The only risk-acceptance path remains `HOLD—OWNER-ACCEPTED CONTAINMENT` (default-off flag · quarantine · non-prod), never a passed gate.

**Final-gate rule — the last material edit is never the only unreviewed edit.** Every gate reviews the *pre-fix* diff. After PM triage, only **REMEDIATE** findings are fixed. **If the changeset's frontier firing is unspent, the remediation delta receives it as a fold-check** (`core/GATES.md` § Model · effort matrix). The approved remediation delta receives one cross-family bookend when available — *code* in diff-mode; *design/core-doc* in design-mode on the full updated artifact — or one same-family cold re-review when the lens is unavailable. The bookend checks approved fixes and regressions; unrelated new findings return to PM triage and are **not** auto-remediated. A structural/substantial approved fix restarts the external gate only when the PM classifies it as such; after the soft stop, that cycle also needs the continuation justification. A clean pass, or one containing only permissible declined/deferred items, closes the ladder.

**Gate continuation — soft stop, never clean-pass chasing.** The initial final gate plus **two PM-approved remediation/bookend cycles** is the target. The PM may stop earlier for diminishing returns. At round 4+ it either stops/escalates or emits `PAST-SOFT-STOP: CONTINUE` plus the required justification; there is no Owner-presence hard stop. Remaining nits and non-material edges are declined or ticketed alongside `GO`. Unresolved structural or Owner-judgment issues terminate as `HOLD + ESCALATE`. An unresolved BLOCKER/HIGH in a required dimension cannot ship as a passed gate — at most `HOLD—OWNER-ACCEPTED CONTAINMENT` on explicit written acceptance, never relabeled `GO`.

**Shipping — any code push.** Any push **containing code** to the live / auto-deploy target needs the **code gate + a named Owner push-GO** (T1: cold + push-GO; T2/T3: cold + external + push-GO) — never a routine code push. **Push-GO follows TIER, not file type: docs-only pushes are free at T0 only — a T1–T3 push (code OR instruction; a prod-write-directing doc like the Runbook tiers by what it directs) needs its tier's gate + the Owner push-GO.** If the pushed code carries a prod-write path, the push-GO authorizes the *deploy* only; each prod write it then performs takes its own named **write-GO** (the two are never merged).
